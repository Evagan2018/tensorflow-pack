The ADD test, explained step by step

We give the runtime a tiny addition problem and check its answer. The test exercises the code supplied by the installed TensorFlow pack, on a simulated microcontroller.

Open the standalone SVG

The example

Input A:          [−3,  0,  0.50, 16]
Input B:        + [ 1, −2,  0.25, −8]
Expected output:  [−2, −2,  0.75,  8]

float32 means 32-bit floating-point numbers. Shape [1, 4] means one row containing four numbers. This is one test case with four output values, not four different operator tests.

Three different things are created

ItemPlain meaning
Model: add.tfliteThe instruction sheet: add the two runtime inputs. It is data describing the calculation, not a standalone executable.
Test data: test_data.hThe embedded model bytes, input numbers, expected answer and accepted numerical tolerance.
Firmware: an .elf fileThe executable program: board startup, the test runner and the TensorFlow runtime/kernel compiled from the installed packs.

Who does what?

ComponentResponsibility
Python + TensorFlow 2.18.0Generate the model on the development computer. Verify that it contains exactly one ADD version 1 operation, with two runtime inputs. Compute reference results using the host interpreter, with default delegates disabled, and cross-check them against NumPy addition.
ResolverThe firmware calls AddAdd() to make ADD available. Only this operation is registered.
TFLM MicroInterpreterLoads the model, allocates tensors in a 32 KiB arena, receives the inputs and executes ADD. This arena size is a conservative starting allocation, not a measured minimum.
CMSIS-Toolbox + GCCBuild the consumer with the TensorFlow pack's Reference kernel component and the board's startup/stdio support.
FVPA Fixed Virtual Platform: software that simulates the Corstone-320 hardware. The Cortex-M CPU runs this test. No physical board is required and the NPU is not used. The workflow activates the existing Arm license environment before launching the FVP.
Firmware checker + host result parserThe firmware checks output count, type, shape and each number. The host requires one correct case identity, all four value records and a successful summary; it rejects duplicates, missing records, process failure and wall timeout.

What is a pass?

Every output must satisfy |actual − expected| ≤ 0.000001 + 0.000001 × |expected|. Non-finite values fail. The normal run must report ADD_CASE:add_float32_reference:PASS and ADD_SUMMARY:1/1.

Why deliberately insert a wrong answer?

A testbench that always prints PASS is useless. The workflow therefore saves the normal test data, changes the first expected value from −2 to 99, rebuilds and executes again. It must report numerical mismatch and 0/1. A crash or missing summary does not count as detecting the wrong answer. The control run is successful only when it demonstrates that the numerical test fails correctly; it is never reported as a numerical pass.

Dependencies and version scope

This first profile accepts only the existing 1.26.8-rc4 TensorFlow candidate artifacts. Their identities and hashes are recorded. The independently pinned ARM::CMSIS-Ethos-U@1.0.0 pack remains part of dependency verification, but the generated board layer removes its driver component and NPU initialization.

The board files and tool configuration come from the pinned CMSIS-LiteRT commit 84bdb98f2045ce299686364518615177ecb0fe25. The existing Release CI inputs and version-generation logic are unchanged. This profile does not qualify the older 1.26.5_rc3 target or other operators, types, shapes, CMSIS-NN kernels or NPU execution.
